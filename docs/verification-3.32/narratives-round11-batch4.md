## 过程问题（按 Lead 要求补入"机制优于小心"一组）

**教训：把"校验步骤"与"改动步骤"分开，一个失败不会静默跳过另一个。**

上一批（3.32c）我在**同一次工具调用里串联了「修补 + 装配」**，结果修补本身出错时，后续装配链要么没执行、要么在失败状态下继续，导致我多花了两次调用才收尾。本批改为两步走：

1. 先只跑 `build-narratives-batch-3.32.mjs --check`（只为校验，不改任何产物）；
2. 通过后再单独跑「清洗 → 装配 → apply → gz → 校验」。

这与另外两条经验同属一类，可归入同一组：

| 经验 | 反例（"小心"） | 机制（"步骤"） |
|---|---|---|
| 注记清洗 | 手写时提醒自己别抄覆盖句（我连续 5 次失败、机制化后本人又犯 2 次） | 装配前固定跑清洗脚本并记录条数 |
| JSON 构造 | 手写大 payload 的对象字面量（两次尾逗号语法错误、白跑一轮） | 用 `JSON.stringify(对象数组)` 生成文件 |
| 校验与改动分离 | 一次调用里"修补+装配"，前段失败会静默影响后段 | **先 `--check` 只看结果，再单独装配** |

**共同点**：都是把"需要人记住的东西"变成"失败会立刻暴露的步骤"。这与身份反查、核验上限规则是同一条原则——**机制优于小心**。
